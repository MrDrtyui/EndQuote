# EndQuote SaaS MVP — six independently gated slices

## Context and goals

All implementation paths below are relative to `endquote-furniture/`. Today `package.json` builds only a React 19 / Vite 8 / TS 7 / Tailwind 4 SPA. `src/App.tsx` treats everything other than `/` and the `/lab` prefix as a booking. `src/booking/BookingApp.tsx` owns manifest loading, demo title, embedded stages, navigation, browser basket/order reads and submission. `photos.ts` makes browser data URLs; `shop/useStoreNavigation.ts` restores demo orders; `shop/*` uses demo company and pricing. `pricing.ts` already accepts explicit tariffs and rounds each percentage surcharge to 100 ₸ before multiplying by quantity. Reuse this arithmetic and the standalone storefront; do not fork or restyle it.

Build one same-origin Node service serving the compiled SPA/static assets and `/api`, with PostgreSQL as system of record and private S3-compatible object storage. Separate server package/runtime (Node 24 LTS, ESM); retain the frontend toolchain. One owner, one business; KZT, no payment gateway, team roles, marketing redesign, public customer accounts or new 3D assets. An order is a request with an estimate, not payment or appointment confirmation.

**Preservation rule for every slice:** no edits to marketing source/assets, `ShowcaseApp.tsx`, viewer/geometry, styles of the approved storefront, index presentation, manifests, `.blend`/GLBs, thumbnails, or preservation signatures. Before implementation capture current path inventories/hashes and desktop/mobile renders for `/`, `/lab`, `/chistodom`, alias and four iframe stages. Use a temporary test output directory; avoid overwriting reference reports. Compare against this snapshot **and** run/report legacy checks; the documented pre-existing `.blend` revision is not permission to change the file, regenerate a baseline, suppress failures or introduce another difference. No new links or forms on `/`. Permit narrowly scoped booking data bindings and truthful transactional text, not a new client design.

## Dependency-ordered implementation

### 1. Database and owner authentication

**Boundary:** new `server/{src,prisma,tests}`, `server/package*.json`, `server/prisma.config.ts`, local env **example** and ignore rules. No UI changes. Use Fastify, Zod at HTTP/config boundaries, `pg`, matching Prisma CLI/client/adapter-pg 7.10.1; verify package availability and Node24 support before installing, stop on incompatibility. Prisma 7 config supplies migration URL; ESM generated `prisma-client` with explicit output, runtime client uses `PrismaPg` pool. Separate runtime least-privilege and migration roles. One connection pool, graceful shutdown, request IDs; no PII, query parameters, tokens, files or credentials in logs.

Start committed migration history here, not in phase 6. `Owner(id UUID, normalizedEmail UNIQUE, passwordHash, createdAt)`, owner sessions with unique hashed random token, owner FK, issue/idle/absolute expiry and revocation. Argon2id; bounded password length; generic login errors. Rotate tokens on login/password change, revoke all old sessions on credential change, revoke current on logout. HttpOnly Secure SameSite=Lax host-only cookie, Path=/, production HTTPS only; explicit loopback-only dev exception. For all unsafe browser calls enforce exact configured Origin (no permissive CORS), JSON or explicitly expected multipart, session-bound CSRF header, including pre-login anonymous challenge; tokens not in localStorage. Apply body limits and shared Postgres rate buckets with TTL, by IP and normalized account where appropriate (login example 5 failures/15 min/account plus per-IP cap); trust forwarded IP only from configured proxy.

`GET /api/auth/session` → identity/onboarding state or anonymous, CSRF challenge; `POST /api/auth/register`, `/login`, `/logout`; registration accepts email/password only, logs in owner, no business or role argument. Strict Zod schemas; standard `{error:{code,message,fields?}}`, 400 invalid, 401 unauthenticated, 403 forbidden, 409 conflict, 429 + Retry-After; auth/private responses no-store. Gate: fresh isolated Postgres `prisma generate`, `prisma migrate deploy`, `prisma migrate status`; register/login across process restart; invalid CSRF/origin, expired/revoked session, duplicate normalized email and rate caps tested. No mock DB as acceptance.

### 2. Self-service onboarding and tenant boundary

**Boundary:** extend server schema/migrations/auth middleware/tests; new `src/owner/{auth,onboarding}` and API client, lazy exact routes in `src/App.tsx`. Login/register/onboard under `/owner`; incomplete owner can manage account/onboard, cannot query a default business. `POST /api/owner/business` → 201 business + canonical URL; one transaction creates `Business(id UUID, ownerId UNIQUE FK, slug, profile, published=false, trialEndsAt, accessState, catalogRevision)`, slug registry and private copy of validated neutral starting catalog; trial default 14 days from creation UTC. Confirmation step before publishing. Concurrent completion cannot create two tenants.

Canonicalize lowercase ASCII kebab slug, length 3–48; reject ambiguous encodings, delimiters, invalid segments. Shared reserved names include `api`, `owner`, `admin`, `lab`, `clean`, `chistodom`, `assets`, `models`, actual public top-level paths and infrastructure/health routes. Registry unique across canonical and retired names; rename in same transaction, old URL stays unavailable (410, no reassignment, no silent redirect), new URL shown for copying. Gate with racing claims/renames.

Every business-owned row (catalog/config, customer, order, line, upload, status event, etc.) has `businessId NOT NULL` and tenant-scoped unique keys; composite FKs `(businessId,parentId)` to matching unique pairs. Owner repository methods require business scope derived **only** from authenticated owner → business, never client-supplied IDs/slug. Scope lookup/update/count and attachment authorization in the query; foreign IDs return 404. Public reads resolve current slug and published/entitled state independently; serialize only public fields. Test two owners' rows, cross-tenant FK rejection, no unscoped listings or slug injection.

Routing order: API/resources first (missing API = JSON 404, missing asset = ordinary 404), exact `/`, `/lab`, `/chistodom` and `/clean/chistodom` (preserve query/hash and existing alias behavior), owner/admin namespaces, then single valid candidate `/:slug`, otherwise explicit not-found. For unresolved routes use «Страница не найдена»; known unavailable «Витрина сейчас недоступна»; transport failure «Не удалось загрузить витрину. Попробовать ещё раз». Never render ЧистоДом as fallback; until phase 4, live route is explicitly unavailable. No marketing embed treatment on live slugs. Gate: route precedence, invalid paths, standalone/iframe snapshots, two-owner onboarding on real DB.

### 3. Owner workspace and versioned catalog

**Boundary:** `src/owner/*` (scoped styles only), server owner routes/services, schema/migrations/tests. Implement DB order/customer/snapshot tables now to allow true empty states, status operations and seeded disposable integration fixtures before public submissions exist.

`GET /api/owner/summary` returns actual scoped counts by status, defined date window and sum of estimates (not revenue); `GET /orders?status=&cursor=` and `/orders/:id` under `/api/owner`, stable pagination, details include snapshot lines, contact, consent and attachments. `PATCH /orders/:id/status {from,to}` atomically updates valid transitions (new → accepted/cancelled → terminal, accepted → completed/cancelled); conflict on stale state; status history with actor/date. No synthetic metrics or sample production orders.

`GET/PUT /api/owner/catalog` edits service/category names, visibility, model/category mapping, enabled models and base prices for **all 12** manifest IDs, material/soil modifiers and extras/fees. No arbitrary geometry IDs. Validate bounded integer KZT, percentage basis points, duplicates, mappings and enabled references; revision precondition on writes, transaction increments revision on every price/availability change. Explicit adapter converts basis points to existing calculation fractions; reject unsafe totals. Store independently per tenant, not mutable global demo tariffs. `GET/PATCH /api/owner/profile` for name, description, city/area, contacts, logo reference, social links, publish and slug; sanitize output, allowlisted HTTPS social hosts and validated phone, reject unsafe URL schemes. Logo uploads use phase 4's private processing primitive, implemented first here for authenticated owners; only sanitized current logo served via a controlled public branding route for a published business. `PATCH /api/owner/account` email/password with current password and session rotation. Show canonical link + clipboard, honest copy failure fallback; authenticated preview of draft via same UI/read-only adapter (no orders/uploads); link to preview is not public authorization. Wire preview to shared presentation in phase 4.

Gate: verify through UI and DB two owners see different summaries/orders/catalogs; status persists with history; invalid updates roll back, stale revision conflicts; slug/copy, profile and account changes persist, old login/session fails; empty account shows zeros. Mark preview rendering integration pending until next gate.

### 4. Live storefront, pricing, private submissions and media

**Boundary:** new `src/booking/live/*`, thin shared flow/view contracts in `BookingApp.tsx`, `shop/*`, affected booking leaf components and `pricing.ts`; new server public/receipt/storage modules, migrations/tests. Preserve rendered tree, classes, camera/viewer, lighting, textures, model URLs and navigation. Inject profile, catalog, explicit tariff, mode/copy, cart/receipt and submit adapters down to catalog/cards/studio/cart/checkout/confirmation and back/forward navigation. Demo-only imports confined to demo composition; grep for implicit price defaults, demo phone/title/order reads. Keep standalone demo browser-local behavior in its original namespace only; **no server writes**. Marketing embed must never read/write persistent demo/live data, submit/upload or mutate a basket/order outside iframe memory (current `initialOrder` and submit paths need explicit guards); retain original stage presentation. Draft preview also memory-only. Live basket in memory only, reset on business change; contacts/photos/receipts never in Web Storage. Demo «Демонстрационная заявка», live «Предварительная стоимость», «Заявка отправлена» **only after commit**; don't claim browser-local storage, delivery or confirmed visit for live requests.

`GET /api/public/:slug` returns public profile, enabled catalog/tariff, revision and consent version; merge with frozen manifest by model ID. Anonymous scoped checkout session and CSRF via same-origin initialization on live route only. `POST /api/public/:slug/quote {revision,items}` returns validated lines/total. `POST /api/public/:slug/orders` requires Idempotency-Key, same session, expected revision, configurations/quantities, bounded contact fields/date, explicit unchecked-by-default consent + current version, finalized upload IDs. No client amount accepted. At commit lock/recheck current business entitlement, publication, revision and enabled selections; recompute using explicit tariff, validity and bounds; 409 `PRICE_CHANGED` returns fresh quote/revision or unavailable items for **explicit reconfirmation**. Same check for consent version. Date is requested local service date, not scheduled appointment.

Atomic customer upsert by `(businessId,normalizedPhone)`, order with immutable contact/business/consent version+timestamp, line snapshots of model/category/service labels, configuration, per-component rates and amounts, quantity, KZT and total/revision; customer updates never rewrite history. Attach upload IDs exactly once in transaction. Unique `(businessId,checkoutSessionId,idempotencyKey)` with normalized payload digest: first commit 201, identical retry returns same receipt/order even after revision changes (check committed key before reprocessing), different payload 409; serialize racing retries. Clear cart only after success. Private same-session `GET /api/public/:slug/receipts/:opaqueId`; server-bound random receipt ID alone isn't authorization; no public lookup by phone/sequential ID, no shared caches, URL secrets or PII in query strings. Owner detail separate.

Server-mediated multipart `POST /api/public/:slug/uploads` with checkout grant; default 3 photos, ≤10 MB each plus aggregate/request/pixel limits, streaming byte caps, MIME + magic + bounded decode, JPEG/PNG/WebP only, re-encode strip metadata, randomized tenant keys, no SVG/raw filenames or base64 DB data. Equivalent owner-only logo endpoint with separate purpose/limits. Store validated bytes in private S3 bucket; DB records purpose, tenant, uploader/session, size, key and staged/attached state. Verify same tenant/session/purpose, expiry and unclaimed status at checkout. Anonymous order receipts omit media URLs. No public ACLs, listing or client S3 credentials. Delete unclaimed objects after 24h; handle failed uploads/DB commits with compensating delete + reconciliation, including objects lacking DB row; enforce rate/storage quotas. Document retention and consent wording for operator review before launch.

Implementation constraint: use Node24-compatible sharp with allowlisted decoder, input byte/pixel and encoded output byte caps; strip metadata. Server-only S3 Put/Get/Delete; **always stream order photos through owner-scoped handlers**, never return signed/bearer URLs, bucket keys or storage credentials to the browser. Only the current sanitized logo has a public same-origin branding endpoint. Keep objects small enough for single Put; abort incomplete body processing on disconnect. Tag staged keys for reconciliation, unlink replaced logos only after DB commit.

**Public intake contract:** Route alone selects mode: query flags cannot enable embed/demo on a live slug, enable live writes on a demo route, or turn an unknown slug into anything but 404. On B's public slug even a signed-in owner A is a customer of **B**; ignore owner identity for public tenant resolution. Mint a random intake-attempt ID within B's anonymous checkout session, reuse it for retries of that attempt, bind staged uploads to `(businessId, checkoutSessionId, attemptId)` and require all three to match. Within the submission transaction serialize against publication, tariff and access changes; check server time **after acquiring the lock**, read one coherent revision, and commit every order line or none. For a previously committed identical key/attempt/digest, return only a non-PII acknowledgement (`alreadySubmitted`, opaque reference), even if access has since expired or tariffs changed. Permit that lookup before the new-intake guard, but never bypass session/attempt validation or the separate receipt read authorization.

Deterministic gate: use fixed data, a controlled server clock and transaction barriers rather than sleeps. Submit on B while signed in as A; assert all rows belong to B. Vary query flags on both routes and an unknown slug. Race identical submits and a tariff edit in both lock orders; assert exactly one complete snapshot at one revision or zero writes plus reconfirmation. Hold submission across the expiry boundary and assert denial after lock acquisition; replay an earlier committed request after expiry/reprice and assert acknowledgement only. Swap staged IDs across attempts in the same tenant and across tenants; attempt receipt/photo reads from unrelated sessions; require denial with no partial writes.

Gate: use real private S3 + Postgres. Anonymous direct object read denied; allowed image stored/retrieved by right owner, mismatched bytes/oversize/reused foreign uploads rejected. Interrupt upload, inject DB failure after successful Put, advance staged TTL and run cleanup twice: no dangling references, orphan bytes removed, attached photos undisturbed. Verify replaced logo no longer served, cross-owner and anonymous photo reads denied, browser responses contain no storage tokens/URLs. Live does not consume demo data; identical concurrent submit writes one order/customer/attachment set, tariff edit prompts re-confirmation; old order retains old price. Draft preview shows owner's saved draft, cannot submit. Test each embed stage including attempted checkout produces no persistent write.

### 5. Entitlements and separate platform administration

**Boundary:** central server policy and admin auth/routes/CLI/audit, owner access banner, lazy `src/admin/*`, tests/migrations. Basic access guard exists before public writes ship; complete lifecycle here. Effective status computed against server UTC at request and commit time (no dependency on cron). Trial before end and active before optional paid-through timestamp: owner edits/publishes, public reads/quotes/uploads/orders if published. Equality at deadline = expired. Expired: owner login/account/security and read existing dashboard/orders/attachments, copy link and view read-only private preview; block catalog/profile/status mutations and public intake/branding, no new uploads; public storefront shows unavailable, no tariff/PII. Unpublished likewise unavailable. Already-issued, unexpired session-bound receipts may read minimal confirmation independent of publication/expiry, not after credential expiry. Unknown/retired URLs never resolve to a different business. Demo, lab and marketing independent of policy/DB. Owner mutation denied with 403 `SUBSCRIPTION_EXPIRED`; known unavailable public API 410, unknown 404, outage 503/retry.

Separate `PlatformAdmin` identities/sessions/cookie/guard and `/admin` login; out-of-band local operator CLI prompts for initial email/password without echo/logs, hash immediately, refuse duplicate bootstrap, credentials never via CLI args/seed/defaults. No public role assignment, owner upgrade, or owner session accepted; no impersonation. Admin API lists paginated business name, owner identifier, subscription and dates; `PATCH /api/admin/businesses/:id/access {expectedVersion,state,endsAt,reason}` trial extension, activate or expire, audited actor/time/old/new/reason transactionally; no browsing order PII or photos. Same CSRF/origin, rotation, rate and logout rules for admin. No fake billing/payments.

Gate: clock-controlled boundary tests for each matrix operation including stale open checkout; separate owner/admin cookie jars, register with `role` rejected, simultaneous admin updates conflict, reactivation restores correct tenant only and audit survives restart.

No deployment in this plan. Build frontend with supported current toolchain, package `dist/` with compiled Node24 server and generated Prisma client/required native runtime dependencies. Production serves only `dist` and explicit API routes, never repository root/env/private uploads. Exact resource/media types and 404s, HTML fallback for recognized navigation only with appropriate unknown/unavailable HTTP status, no API fallback; Vite dev same-origin proxy. Public static/demo paths work during backend outage. TLS reverse proxy, allowlisted Host/origin, no-store for private data, same-origin framing compatible with marketing iframe, health/liveness and dependency readiness without secrets. DB/S3 not exposed publicly. Document config, startup, one-shot migration job, admin bootstrap, backups and restore, access logs/redaction, quotas/cleanup and rotation; no production `db push`/reset/auto-seeding.

## Risks and rollback

* Shared booking flow is the highest regression risk: extract injectable values before changing behavior, compare after each edit, disable live routes rather than falling back to demo.
* Releases must keep older service binary compatible through additive migrations; backfill then constrain, defer destructive changes. Withdraw new registrations/intake during rollback; keep accepted orders, idempotency rows, slug tombstones and media. Roll back application image only when schema compatibility verified, otherwise forward-fix. Restore backups only to a fresh target and reconcile accepted requests before cutover.
* Public abuse, sensitive photos and expiration races require quotas, bounded decode, private grants and transaction-time checks, not just disabled buttons. Block launch if operator has not reviewed consent, retention, backup permissions, HTTPS, credential provisioning or restore evidence.

## Acceptance criteria

- 1. Node24 server authenticates owners with real PostgreSQL migrations, revocable sessions, CSRF protection and rate limits without downgrading the frontend.
- 2. Two owners self-onboard isolated businesses; reserved, duplicate, retired and unknown slugs cannot reveal another storefront or fall through to the demo.
- 3. Owners manage real orders, statuses, statistics, profiles, account settings and independent complete tariffs, and can copy and preview their storefront.
- 4. The unchanged standalone UI submits consented, server-priced, idempotent live orders with immutable snapshots and private validated S3 photos; demo and iframe never write live data.
- 5. Trial, active and expired access is enforced at the server; only separately provisioned platform admins change access, with an audit trail.
- 6. Fresh and upgrade migrations, private storage, restore, packaged same-origin desktop/mobile two-owner E2E and preservation checks pass with no new baseline drift.
